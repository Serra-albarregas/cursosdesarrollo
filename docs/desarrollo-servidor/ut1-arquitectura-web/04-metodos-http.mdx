# 4. Métodos de petición HTTP

El **método** (o *verbo*) expresa la **intención** de la petición sobre el recurso indicado en la
ruta. Elegirlo bien no es una formalidad: de él dependen el comportamiento de las cachés, de los
proxies, de los navegadores y de los mecanismos de reintento.

## 4.1. Tabla de referencia

| Método | Intención | ¿Seguro? | ¿Idempotente? | ¿Cacheable? | ¿Cuerpo en petición? |
|--------|-----------|:--------:|:-------------:|:-----------:|:--------------------:|
| `GET` | Obtener un recurso | ✅ | ✅ | ✅ | No |
| `HEAD` | Como GET, sólo cabeceras | ✅ | ✅ | ✅ | No |
| `OPTIONS` | Consultar capacidades | ✅ | ✅ | ❌ | No |
| `TRACE` | Eco de diagnóstico | ✅ | ✅ | ❌ | No |
| `POST` | Crear / procesar | ❌ | ❌ | Raramente | Sí |
| `PUT` | Reemplazar por completo | ❌ | ✅ | ❌ | Sí |
| `PATCH` | Modificar parcialmente | ❌ | ❌* | ❌ | Sí |
| `DELETE` | Eliminar | ❌ | ✅ | ❌ | Opcional |

\* `PATCH` puede diseñarse idempotente, pero el protocolo no lo garantiza.

## 4.2. Las tres propiedades

### Seguro (*safe*)

Un método es **seguro** si **no modifica el estado** del servidor. Es de sólo lectura.

```html
<!-- PETICIÓN GET A BORRAR: NUNCA -->
<a href="/alumnos/42/borrar">Eliminar alumno</a>
```

### Idempotente

Un método es **idempotente** si ejecutarlo **N veces produce el mismo estado final** que
ejecutarlo una sola vez.

- `DELETE /alumnos/42` — el alumno queda borrado; repetirlo no cambia nada más. Idempotente.
- `POST /alumnos` — cada llamada crea un alumno nuevo. **No** idempotente.

Esto importa cuando la red falla: si un cliente no recibe respuesta, sólo puede **reintentar sin
riesgo** una operación idempotente.

### Cacheable

Una respuesta es **cacheable** si puede almacenarse y reutilizarse en peticiones posteriores.
`GET` lo es por defecto; los métodos de escritura, no.

:::note
Todo depende de tu implementación
Que `GET` sea "seguro" es una **convención del protocolo**, no una garantía técnica. Si programas un
`@GetMapping` que borra registros, nada te lo impide — y habrás roto el contrato de HTTP con
consecuencias muy difíciles de depurar.
:::

## 4.3. Los métodos uno a uno

### GET

Solicita la representación de un recurso. Los parámetros van en la *query string*, nunca en el
cuerpo.

```http
GET /api/alumnos?curso=2DAW&orden=nombre HTTP/1.1
Host: api.centro.es
Accept: application/json
```

### POST

Envía datos para que el servidor los procese. Es el método "comodín": creación de recursos,
formularios, inicios de sesión, operaciones que no encajan en el resto.

```http
POST /api/alumnos HTTP/1.1
Content-Type: application/json

{"nombre":"Lucía Márquez","curso":"2DAW"}
```

Respuesta correcta a una creación:

```http
HTTP/1.1 201 Created
Location: /api/alumnos/42
```

### PUT

Sustituye **por completo** el recurso. Los campos que no envíes se consideran ausentes.

```http
PUT /api/alumnos/42 HTTP/1.1
Content-Type: application/json

{"nombre":"Lucía Márquez","email":"lucia@centro.es","curso":"2DAW"}
```

### PATCH

Aplica una **modificación parcial**:

```http
PATCH /api/alumnos/42 HTTP/1.1
Content-Type: application/merge-patch+json

{"curso":"2DAM"}
```

| | `PUT` | `PATCH` |
|---|---|---|
| Alcance | Recurso completo | Campos indicados |
| Campos omitidos | Se borran/resetean | Se mantienen |
| Idempotencia | Garantizada | No garantizada |

### DELETE

**Elimina** un recurso.

```http
DELETE /api/alumnos/42 HTTP/1.1
```

### HEAD y OPTIONS

- `HEAD`: idéntico a `GET` pero el servidor devuelve **sólo cabeceras**. Útil para comprobar si un
  recurso existe o su tamaño sin descargarlo.
- `OPTIONS`: informa de qué métodos admite un recurso. Es la base de las **peticiones de
  comprobación previa (*preflight*) de CORS**.

```http
OPTIONS /api/alumnos HTTP/1.1
---
HTTP/1.1 204 No Content
Allow: GET, POST, OPTIONS
```
