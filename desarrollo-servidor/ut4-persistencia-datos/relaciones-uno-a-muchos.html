8. Relaciones entre entidades (I): @ManyToOne y @OneToMany

Hasta ahora, el curso de un alumno era un simple texto ("1DAW"). Pero un curso es algo más que un nombre: tiene una descripción, varios alumnos, y en el futuro tendrá más datos. En una base de datos relacional eso se resuelve con dos tablas relacionadas por una clave foránea. En esta página vemos cómo expresar esa relación en JPA.

8.1. El modelo: un curso, muchos alumnos​

Es una relación uno a muchos: un curso tiene muchos alumnos, y cada alumno pertenece a un único curso. Visto desde el otro lado, es muchos a uno: muchos alumnos tienen el mismo curso.

En JPA, los dos lados de esa relación tienen su anotación:

Desde la claseAnotaciónSe lee como
Alumno@ManyToOneMuchos alumnos pertenecen a un curso
Curso@OneToManyUn curso tiene muchos alumnos

En la base de datos, sin embargo, solo hay una clave foránea: la columna curso_id de la tabla alumnos.

8.2. @ManyToOne y @JoinColumn​

La entidad Curso es una entidad como las que ya conocemos:

@Entity
@Table(name = "cursos")
public class Curso {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 10)
    private String nombre;          // "1DAW"

    @Column(length = 100)
    private String descripcion;     // "Primero de Desarrollo de Aplicaciones Web"

    public Curso() { }

    // getters y setters
}

Y en Alumno, el atributo curso pasa de ser un String a ser un Curso, anotado con @ManyToOne:

@NotNull(message = "Debes elegir un curso")
@ManyToOne
@JoinColumn(name = "curso_id", nullable = false)
private Curso curso;
  • @ManyToOne indica que es el lado "muchos" de la relación.
  • @JoinColumn indica cómo se llama la columna de la clave foránea en esta tabla (curso_id), y con nullable = false se exige que todo alumno tenga curso.
  • La anotación de validación cambia de @NotBlank a @NotNull, porque ya no es un texto.

Con ddl-auto=update, Hibernate genera algo parecido a:

create table cursos (
    id bigint not null auto_increment,
    nombre varchar(10) not null,
    descripcion varchar(100),
    primary key (id)
)

create table alumnos (
    id bigint not null auto_increment,
    -- ...resto de columnas...
    curso_id bigint not null,
    primary key (id)
)

alter table alumnos add constraint FK... foreign key (curso_id) references cursos (id)

Usarlo​

Se trabaja con objetos, no con identificadores: para asignar un curso a un alumno se le asigna el objeto Curso, y Hibernate se encarga de rellenar curso_id.

Curso daw1 = cursoRepositorio.save(crearCurso("1DAW", "Primero de Desarrollo de Aplicaciones Web"));

Alumno eva = new Alumno();
eva.setNombre("Eva Soto");
eva.setCurso(daw1);                 // se asigna el objeto, no un texto ni un id
// ... resto de campos
alumnoRepositorio.save(eva);        // inserta el alumno con curso_id = id de daw1

Y se lee navegando por los objetos: alumno.getCurso().getNombre().

nota

El curso debe estar guardado antes Si se asigna a un alumno un Curso que todavía no se ha guardado (su id es null), el guardado falla con un error del estilo object references an unsaved transient instance. Hay que guardar primero el curso, o configurar cascade (lo veremos más abajo).

8.3. @OneToMany y mappedBy: la relación bidireccional​

Con lo anterior ya se puede ir de un alumno a su curso. Pero si se quiere ir al revés (dado un curso, obtener sus alumnos con curso.getAlumnos()), hace falta declarar también el otro lado, con @OneToMany:

@OneToMany(mappedBy = "curso")
private List<Alumno> alumnos = new ArrayList<>();

El atributo clave es mappedBy = "curso". Le dice a JPA: "esta relación ya está definida en la clase Alumno, en su atributo llamado curso; no crees nada más". Es el nombre del atributo de Alumno, no el de la columna.

El lado propietario​

En toda relación bidireccional hay un lado propietario, el que controla la clave foránea, y un lado inverso, que solo es un "espejo" de lectura:

Lado propietarioLado inverso
ClaseAlumnoCurso
Anotación@ManyToOne + @JoinColumn@OneToMany(mappedBy = ...)
Qué haceEs el que escribe curso_id en la base de datosSolo se lee; no guarda nada por sí mismo
Regla generalEl lado "muchos" (el que tiene la clave foránea)El lado "uno", con mappedBy

La consecuencia práctica es muy importante: solo cuenta lo que se asigna en el lado propietario.

curso.getAlumnos().add(eva);        // NO basta: no se guarda ninguna relación
eva.setCurso(curso);                // esto es lo que escribe curso_id

Añadir el alumno a la lista del curso, sin hacer eva.setCurso(curso), no guarda nada. Y al revés, asignar setCurso no actualiza la lista del curso que ya estuviera cargada en memoria. Para que ambos lados estén siempre de acuerdo, se acostumbra a escribir un método auxiliar en Curso:

public void agregarAlumno(Alumno alumno) {
    alumnos.add(alumno);
    alumno.setCurso(this);
}

public void quitarAlumno(Alumno alumno) {
    alumnos.remove(alumno);
    alumno.setCurso(null);
}

¿Unidireccional o bidireccional?​

Solo @ManyToOne (unidireccional)@ManyToOne + @OneToMany (bidireccional)
Se puede ir de alumno a cursoSíSí
Se puede ir de curso a alumnosNo (hay que consultar con el repositorio)Sí, con curso.getAlumnos()
ComplejidadMenorMayor: hay que mantener los dos lados

Si no hace falta recorrer la relación desde el curso, la unidireccional es suficiente y más sencilla. Se añade el lado @OneToMany solo cuando se necesita.

nota

@OneToMany sin mappedBy Si se escribe @OneToMany sin mappedBy, JPA entiende que es una relación unidireccional distinta de la que ya existe con @ManyToOne, y crea una tabla intermedia adicional (cursos_alumnos) para guardarla. Es un error muy habitual: si aparece una tabla que no esperabas, falta el mappedBy.

8.4. Repositorios y datos​

Cada entidad tiene su repositorio:

public interface CursoRepository extends JpaRepository<Curso, Long> {

    Optional<Curso> findByNombre(String nombre);

    List<Curso> findAllByOrderByNombreAsc();
}

Qué cambia respecto a lo anterior​

Cambiar curso de texto a entidad afecta a lo escrito en las páginas anteriores:

Si en una plantilla se deja ${alumno.curso}, no se produce un error: se imprime el toString() del objeto (algo como es.centro...Curso@3f2a1b).

nota

Cambiar el esquema con datos ya creados Si la tabla alumnos ya existía con la columna curso de texto, ddl-auto=update no la convierte: añade la nueva columna curso_id, pero deja la antigua, y las filas que ya existían no tienen un curso válido al que apuntar (la restricción de clave foránea puede incluso fallar al crearse). Durante el desarrollo, lo más sencillo es volver a crear las tablas con el perfil datos (ddl-auto=create) o borrar el volumen de Docker con docker compose down -v.

8.5. Consultas que atraviesan la relación​

Consultas derivadas​

En una consulta derivada, se puede navegar por la relación escribiendo seguidos los nombres de los atributos:

// Alumnos cuyo curso tiene este nombre: a.curso.nombre
List<Alumno> findByCursoNombre(String nombre);

// Alumnos de un curso concreto, dado por su objeto o por su id
List<Alumno> findByCurso(Curso curso);
List<Alumno> findByCursoId(Long cursoId);

long countByCursoId(Long cursoId);

findByCursoNombre se interpreta como "el atributo nombre del atributo curso". Si hubiera ambigüedad (por ejemplo, si Alumno tuviera también un atributo llamado cursoNombre), se puede indicar la separación con un guion bajo: findByCurso_Nombre.

JPQL​

En JPQL se navega con el punto, y se puede enlazar explícitamente con join:

@Query("select a from Alumno a where a.curso.nombre = :nombre order by a.nombre")
List<Alumno> buscarPorNombreDeCurso(@Param("nombre") String nombre);

@Query("""
        select a from Alumno a
        join a.curso c
        where c.nombre = :nombre and a.edad >= :edad
        """)
List<Alumno> buscarMayoresDeUnCurso(@Param("nombre") String nombre, @Param("edad") int edad);

Un join en JPQL se escribe sobre el atributo de la relación (join a.curso c), no sobre columnas con on. Hibernate deduce el resto a partir del mapeo.

8.6. cascade y orphanRemoval​

Por defecto, cada entidad se guarda y se borra por separado. Con cascade, una operación sobre la entidad padre se propaga a las entidades relacionadas:

TipoQué propaga
PERSISTAl guardar la entidad nueva, se guardan también las nuevas relacionadas
MERGEAl actualizar la entidad, se actualizan también las relacionadas
REMOVEAl borrar la entidad, se borran también las relacionadas
ALLTodas las anteriores

Y orphanRemoval = true hace que, si se quita un elemento de la colección, ese elemento se borre de la base de datos (queda "huérfano" y se elimina).

Tiene sentido cuando los hijos no existen por sí solos: no hay una línea de pedido sin su pedido.

@Entity
public class Pedido {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToMany(mappedBy = "pedido", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<LineaPedido> lineas = new ArrayList<>();
}

Al guardar el Pedido, se guardan sus líneas; al borrarlo, se borran; y al quitar una línea de la lista, se elimina de la base de datos.

En nuestro caso, no lo activamos. Un alumno sí existe por sí solo y borrar un curso no debe borrar a sus alumnos de forma silenciosa. Sin cascade, intentar borrar un curso que todavía tiene alumnos falla con un error de clave foránea, que es justo lo que queremos: antes de borrar el curso hay que decidir qué se hace con sus alumnos.

nota

Cuidado con REMOVE y ALL Es la parte de cascade que más datos puede borrar sin avisar. Úsala solo cuando los hijos dependan por completo del padre.

8.7. Mostrar la relación en las plantillas​

El curso de cada alumno​

Basta con navegar por los objetos en la expresión:

<tr th:each="alumno : ${pagina.content}">
    <td th:text="${alumno.nombre}">Nombre</td>
    <td>
        <a th:href="@{/cursos/{id}(id=${alumno.curso.id})}" th:text="${alumno.curso.nombre}">1DAW</a>
    </td>
    <td th:text="${alumno.edad}">Edad</td>
</tr>

Si el curso pudiera ser null, se usa la navegación segura de la Unidad 2: ${alumno.curso?.nombre}.

Un curso y sus alumnos​

@Controller
@RequestMapping("/cursos")
public class CursosController {

    private final CursoRepository repositorio;

    public CursosController(CursoRepository repositorio) {
        this.repositorio = repositorio;
    }

    @GetMapping
    public String listar(Model model) {
        model.addAttribute("cursos", repositorio.findAllByOrderByNombreAsc());
        return "cursos";
    }

    @GetMapping("/{id}")
    public String detalle(@PathVariable Long id, Model model) {
        Curso curso = repositorio.findById(id)
                .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));
        model.addAttribute("curso", curso);
        return "curso-detalle";
    }
}

    <li th:each="alumno : ${curso.alumnos}" th:text="${alumno.nombre}">Alumno</li>

<p th:if="${#lists.isEmpty(curso.alumnos)}">Este curso no tiene alumnos.</p>
nota

La lista de alumnos se carga al usarla La colección curso.alumnos no se carga junto con el curso: Hibernate la recupera con una consulta adicional en el momento en que la plantilla la recorre (carga perezosa o lazy). Funciona porque Spring Boot mantiene la conexión abierta mientras se genera la vista. En el listado de cursos, esto significa una consulta extra por cada curso. La siguiente página explica este comportamiento y sus límites.

nota

Los formularios con relaciones Un formulario que permita elegir el curso de un alumno (un <select> con los cursos disponibles) plantea problemas propios, como convertir el identificador recibido en un objeto Curso. Los resolveremos en el ejemplo integrador.

SíntomaCausa probableSolución

not-null property references a null or transient valueSe intenta guardar un alumno sin cursoAsigna el curso antes de guardar
Cannot add or update a child row: a foreign key constraint failsEl curso_id no corresponde a ningún cursoComprueba que el curso existe
Cannot delete or update a parent row: a foreign key constraint fails (DataIntegrityViolationException)Se intenta borrar un curso que todavía tiene alumnosComprueba antes si tiene alumnos (por ejemplo, con countByCursoId) y decide qué hacer
Aparece una tabla inesperada (cursos_alumnos)Falta mappedBy en el @OneToManyAñade mappedBy = "curso"
curso.getAlumnos() no incluye al alumno recién guardadoSolo se asignó un lado de la relaciónAsigna setCurso y usa un método auxiliar que mantenga las dos listas
Field 'curso' doesn't have a default valueLa tabla conserva la columna curso antiguaVuelve a crear las tablas (perfil datos)
