9. Relaciones entre entidades (II): @ManyToMany, @OneToOne y tipo de carga

En la página anterior vimos la relación más habitual, la de uno a muchos. Quedan otras dos formas de relacionar entidades: muchos a muchos (un alumno cursa varias asignaturas, y una asignatura la cursan muchos alumnos) y uno a uno (un alumno tiene un carné de biblioteca, y cada carné es de un alumno). Además, veremos cuándo se cargan los datos relacionados, y cómo evitar los problemas más habituales de las relaciones bidireccionales.

9.1. Muchos a muchos: @ManyToMany​

El modelo​

Un alumno cursa varias asignaturas, y cada asignatura la cursan varios alumnos. En una base de datos relacional, esta relación no se puede expresar con una sola clave foránea: hace falta una tabla intermedia que guarde las parejas (alumno, asignatura).

La tabla alumno_asignatura tiene dos columnas, ambas claves foráneas, y la pareja de las dos es su clave primaria. No hay ninguna entidad que la represente: JPA la gestiona por su cuenta.

La entidad Asignatura​

@Entity
@Table(name = "asignaturas")
public class Asignatura {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 50)
    private String nombre;

    @Column(nullable = false)
    private Integer horas;

    @ManyToMany(mappedBy = "asignaturas")
    private Set<Alumno> alumnos = new HashSet<>();

    public Asignatura() { }

    // getters y setters
}

El lado propietario: @JoinTable​

Como en toda relación bidireccional, uno de los lados es el propietario. Aquí lo es Alumno, y es donde se describe la tabla intermedia con @JoinTable:

@ManyToMany
@JoinTable(
        name = "alumno_asignatura",
        joinColumns = @JoinColumn(name = "alumno_id"),
        inverseJoinColumns = @JoinColumn(name = "asignatura_id"))
private Set<Asignatura> asignaturas = new HashSet<>();
ElementoQué indica
nameEl nombre de la tabla intermedia
joinColumnsLa columna que apunta a esta entidad (alumno_id)
inverseJoinColumnsLa columna que apunta a la otra entidad (asignatura_id)

En Asignatura, el lado inverso solo lleva mappedBy = "asignaturas", el nombre del atributo en Alumno, igual que vimos con @OneToMany.

nota

Set en lugar de List En las relaciones muchos a muchos se usa Set. Con una List, Hibernate no puede identificar cada fila de la tabla intermedia, así que ante cualquier cambio borra todas las filas de ese alumno y las vuelve a insertar. Un Set evita ese trabajo y, además, impide duplicados. Para que funcione bien, las entidades dentro del Set necesitan equals y hashCode correctos, algo que vemos en el apartado 9.7.

Mantener los dos lados​

Igual que en la página anterior, solo cuenta el lado propietario (Alumno), pero conviene mantener ambos sincronizados con métodos auxiliares:

public void agregarAsignatura(Asignatura asignatura) {
    asignaturas.add(asignatura);
    asignatura.getAlumnos().add(this);
}

public void quitarAsignatura(Asignatura asignatura) {
    asignaturas.remove(asignatura);
    asignatura.getAlumnos().remove(this);
}

Usarlo​

Alumno eva = alumnoRepositorio.findById(1L).orElseThrow();
Asignatura programacion = asignaturaRepositorio.findByNombre("Programación").orElseThrow();

eva.agregarAsignatura(programacion);
alumnoRepositorio.save(eva);       // inserta una fila en alumno_asignatura

Al guardar o borrar un alumno, Hibernate actualiza solas las filas de la tabla intermedia.

Cuidado con el borrado​

  • Borrar un alumno es sencillo: como es el lado propietario, Hibernate elimina también sus filas de la tabla intermedia.
  • Borrar una asignatura que todavía tiene alumnos falla con un error de clave foránea: al ser el lado inverso, Hibernate no toca la tabla intermedia. Antes hay que desvincularla de sus alumnos (con quitarAsignatura desde cada uno).
  • No uses cascade con REMOVE ni ALL en un @ManyToMany. Los elementos relacionados se comparten: borrar un alumno borraría también las asignaturas, que otros alumnos siguen cursando.
nota

Cuando la relación tiene datos propios Si lo que se guarda en la relación tiene información propia (la nota que obtiene cada alumno en cada asignatura, o la fecha de matrícula), un @ManyToMany no sirve, porque la tabla intermedia no puede tener más columnas. Se resuelve creando una entidad intermedia (por ejemplo, Matricula, con alumno, asignatura y nota), con un @ManyToOne hacia cada lado. En la práctica, es lo que más se acaba necesitando.

9.2. Consultas con muchos a muchos​

Se navega por la colección igual que por una relación sencilla:

// Alumnos que cursan una asignatura
List<Alumno> findDistinctByAsignaturasNombre(String nombre);

// En JPQL
@Query("""
        select distinct a from Alumno a
        join a.asignaturas s
        where s.nombre = :nombre
        """)
List<Alumno> buscarPorAsignatura(@Param("nombre") String nombre);

distinct evita que un alumno aparezca repetido si una consulta lo encuentra por varias asignaturas.

9.3. Uno a uno: @OneToOne​

En una relación uno a uno, cada elemento de un lado se corresponde con como máximo uno del otro. Como ejemplo, el carné de biblioteca de un alumno:

@Entity
@Table(name = "carnets")
public class CarnetBiblioteca {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 10)
    private String numero;

    @Column(name = "fecha_alta", nullable = false)
    private LocalDate fechaAlta;

    public CarnetBiblioteca() { }

    // getters y setters
}

Y en Alumno:

@OneToOne(cascade = CascadeType.ALL, orphanRemoval = true)
@JoinColumn(name = "carnet_id", unique = true)
private CarnetBiblioteca carnet;
  • @OneToOne indica la relación. Aquí Alumno es el lado propietario: su tabla tiene la columna carnet_id.
  • unique = true en la columna garantiza que dos alumnos no compartan el mismo carné: sin ello, la base de datos aceptaría una relación "uno a muchos" disfrazada.
  • cascade = ALL y orphanRemoval = true: aquí sí tienen sentido. El carné no existe por sí solo, depende de su alumno: al guardar el alumno se guarda el carné, y al borrarlo (o al quitarle el carné) se elimina.
CarnetBiblioteca carnet = new CarnetBiblioteca();
carnet.setNumero("B-0001");
carnet.setFechaAlta(LocalDate.now());

alumno.setCarnet(carnet);
alumnoRepositorio.save(alumno);      // guarda también el carné, gracias al cascade

El carné es opcional: un alumno sin carné simplemente tiene carnet a null.

nota

Relación bidireccional Si hiciera falta ir del carné a su alumno, se añadiría en CarnetBiblioteca un @OneToOne(mappedBy = "carnet"). Pero ese lado inverso tiene una limitación: Hibernate no puede cargarlo de forma perezosa, porque necesita comprobar si existe para saber si vale null. Por eso, y por simplicidad, preferimos la relación unidireccional.

9.5. Cuándo se cargan los datos relacionados: LAZY y EAGER​

Al cargar un alumno, ¿debe cargarse también su curso? ¿Y sus asignaturas? Es lo que decide el tipo de carga (fetch):

TipoQué hace
FetchType.EAGER (inmediata)Los datos relacionados se cargan junto con la entidad
FetchType.LAZY (perezosa)Los datos relacionados se cargan solo cuando se usan por primera vez

Cada anotación tiene un valor por defecto:

RelaciónCarga por defecto
@ManyToOneEAGER
@OneToOneEAGER
@OneToManyLAZY
@ManyToManyLAZY

Se cambia con el atributo fetch:

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "curso_id", nullable = false)
private Curso curso;

Cómo funciona la carga perezosa​

Con LAZY, el atributo no contiene el objeto real, sino un sustituto (proxy) generado por Hibernate: un objeto del mismo tipo que, al llamar a cualquiera de sus métodos por primera vez, lanza la consulta y carga los datos de verdad. Es la razón por la que, en la página sobre entidades, indicamos que las clases no pueden ser final. En las colecciones (@OneToMany, @ManyToMany) ocurre algo parecido: el Set es un objeto especial de Hibernate que se rellena al recorrerlo.

Qué conviene usar​

La recomendación general es usar LAZY en todas las relaciones y pedir explícitamente los datos relacionados en las consultas que realmente los necesitan. La carga EAGER parece cómoda, pero trae siempre datos que quizá no se van a usar, y puede multiplicar el número de consultas.

El problema de las N+1 consultas​

Supongamos un listado de 20 alumnos que muestra el nombre de su curso. Con la relación en LAZY:

  1. Una consulta recupera los 20 alumnos.
  2. Al mostrar alumno.curso.nombre, Hibernate lanza una consulta por cada curso distinto que todavía no tenga cargado.

Son 1 + N consultas, en lugar de una sola. Es el llamado problema de las N+1 consultas, y es la causa más frecuente de aplicaciones lentas con JPA. Con EAGER también ocurre: las consultas de Spring Data (findAll, derivadas, @Query) no combinan automáticamente los datos relacionados, y Hibernate los pide aparte.

Se soluciona pidiendo los datos relacionados dentro de la misma consulta, con join fetch:

@Query("select a from Alumno a join fetch a.curso")
List<Alumno> listarConCurso();

O, sin escribir JPQL, con @EntityGraph, que indica qué relaciones cargar junto al resultado:

@EntityGraph(attributePaths = {"curso"})
List<Alumno> findByTurno(Turno turno);

Con cualquiera de las dos, el listado necesita una sola consulta (con un join), y la carga perezosa de la relación deja de ser un problema.

LazyInitializationException​

Tiene una contrapartida: los datos perezosos solo se pueden cargar mientras la conexión con la base de datos sigue abierta. Si se intenta usarlos después, Hibernate lanza una excepción del tipo LazyInitializationException: could not initialize proxy - no Session. En nuestras páginas web no la hemos visto todavía porque Spring Boot mantiene la conexión abierta mientras se genera la vista (spring.jpa.open-in-view, activada por defecto), pero hay situaciones en las que aparece. La siguiente página explica cuándo y cómo evitarla.

Con LAZY, las plantillas siguen funcionando Si en la página anterior dejaste @ManyToOne con su carga por defecto, cámbiala a LAZY y comprueba que los listados y las fichas se siguen viendo igual. La diferencia está en las consultas que se lanzan, que puedes ver en la consola gracias a show-sql.

9.6. Bucles infinitos en toString​

En una relación bidireccional, cada lado apunta al otro. Si el toString de las dos clases incluye la relación, una llamada a cualquiera de ellos no termina nunca:

// En Curso
@Override
public String toString() {
    return "Curso{nombre=" + nombre + ", alumnos=" + alumnos + "}";    // llama a Alumno.toString()
}

// En Alumno
@Override
public String toString() {
    return "Alumno{nombre=" + nombre + ", curso=" + curso + "}";       // llama a Curso.toString()
}

curso.toString() llama a alumno.toString(), que llama a curso.toString()..., hasta que la pila se desborda y se produce un StackOverflowError.

La regla es sencilla: el toString de una entidad no debe incluir sus relaciones, o al menos solo uno de los lados. Lo más seguro es limitarse a los atributos propios:

@Override
public String toString() {
    return "Curso{id=" + id + ", nombre='" + nombre + "'}";
}

Además de evitar el bucle, así toString no dispara la carga perezosa de colecciones enteras al imprimir un objeto en un registro.

El mismo problema ocurre si algún día se convierte una entidad en JSON (por ejemplo, desde un @RestController): cada lado volvería a incluir al otro indefinidamente. La solución habitual es no devolver entidades, sino clases específicas con los datos necesarios.

9.7. equals y hashCode en entidades​

Cuando las entidades se guardan en un Set (como las asignaturas de un alumno), el Set usa equals y hashCode para decidir si dos objetos son "el mismo". Y ahí hay una trampa: la implementación por defecto de Java compara referencias, así que dos objetos que representan la misma fila, cargados en momentos distintos, se consideran distintos.

Tampoco funciona bien basarlos en el id, que es lo primero que se piensa: un objeto nuevo tiene id a null, y su valor cambia al guardarlo, lo que cambia su hashCode y puede dejar el objeto "perdido" dentro de un HashSet.

La opción más práctica es basarlos en una clave natural: un atributo que identifique a la entidad, sea único y no cambie. Aquí, el nombre de la asignatura:

@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Asignatura otra)) return false;
    return Objects.equals(nombre, otra.getNombre());
}

@Override
public int hashCode() {
    return Objects.hash(nombre);
}

Dos detalles importantes:

  • Se compara con instanceof y no con getClass(), porque con la carga perezosa el objeto puede ser un proxy, una subclase de Asignatura, y getClass() daría una clase distinta.
  • De la otra entidad se leen los datos con el getter (otra.getNombre()) y no accediendo al campo (otra.nombre): si otra es un proxy sin inicializar, su campo está vacío.
EntidadPosible clave natural
Asignaturanombre
Cursonombre
Alumnoemail
nota

Solo si hace falta equals y hashCode solo son imprescindibles para las entidades que se guardan en un Set o se usan como clave de un Map. Si una entidad no tiene una clave natural clara, es mejor no sobrescribirlos que hacerlo mal.
