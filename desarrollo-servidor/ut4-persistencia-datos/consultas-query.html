6. Consultas con @Query

Las consultas derivadas del nombre del método son muy cómodas, pero tienen un límite: cuando la consulta se complica, el nombre se vuelve ilegible. Para esos casos, Spring Data JPA permite escribir la consulta a mano con la anotación @Query.

6.1. Una consulta escrita por nosotros​

Con @Query, la consulta va en una cadena de texto sobre el método del repositorio:

public interface AlumnoRepository extends JpaRepository<Alumno, Long> {

    @Query("select a from Alumno a where a.curso = :curso and a.edad >= :edadMinima order by a.nombre")
    List<Alumno> buscarPorCursoYEdadMinima(@Param("curso") String curso,
                                           @Param("edadMinima") int edadMinima);
}

Al llevar @Query, Spring no interpreta el nombre del método: se puede llamar como se quiera, y conviene que describa lo que hace de forma legible (buscarPorCursoYEdadMinima en lugar de findByCursoAndEdadGreaterThanEqualOrderByNombre).

Cuando la consulta es larga, se puede escribir en varias líneas con un bloque de texto de Java (entre """), que hace que se lea mucho mejor:

@Query("""
        select a from Alumno a
        where a.curso = :curso
          and a.edad >= :edadMinima
        order by a.nombre
        """)
List<Alumno> buscarPorCursoYEdadMinima(@Param("curso") String curso,
                                       @Param("edadMinima") int edadMinima);

6.2. JPQL: SQL sobre objetos​

El lenguaje de estas consultas se llama JPQL (Jakarta Persistence Query Language). Se parece mucho a SQL, con una diferencia fundamental: consulta clases y atributos, no tablas y columnas.

SQLJPQL
Qué se consultaLa tabla alumnosLa clase Alumno
Columnas / atributosfecha_nacimientoa.fechaNacimiento
Seleccionar todoselect * from alumnosselect a from Alumno a
AliasOpcionalNecesario (aquí, a)
Mayúsculas y minúsculasSin distinciónLos nombres de clases y atributos sí las distinguen; las palabras clave (select, where) no
Dependencia de la base de datosCada una tiene sus particularidadesEs el mismo para cualquier base de datos

La misma consulta en los dos lenguajes:

-- SQL
select * from alumnos where curso = '2DAW' order by nombre
-- JPQL
select a from Alumno a where a.curso = '2DAW' order by a.nombre

La parte fácil de recordar: en JPQL se escribe lo que hay en el código Java: el nombre de la clase (Alumno) y el de sus atributos (fechaNacimiento), nunca el de la tabla o el de las columnas.

nota

JPQL y HQL Hibernate tiene su propia versión ampliada, llamada HQL, que incluye JPQL y añade algunas funciones. Lo que se ejecuta en @Query es en realidad HQL, aunque en esta unidad solo usaremos la parte común, la de JPQL.

6.3. Parámetros​

Los valores variables no se escriben dentro de la cadena, sino que se pasan como parámetros. Hay dos formas.

Parámetros nombrados (la recomendada)​

Se escribe :nombre en la consulta y se asocia al parámetro del método con @Param:

@Query("select a from Alumno a where a.curso = :curso")
List<Alumno> buscarPorCurso(@Param("curso") String curso);

El texto de @Param debe coincidir con el que va tras los dos puntos. Es la forma más clara, porque cada parámetro tiene nombre y el orden en que se escriben no importa.

nota

¿Y si se olvida @Param? En un proyecto de Spring Boot creado con Spring Initializr, los nombres de los parámetros del método se conservan al compilar, y Spring puede deducirlos sin @Param. Aun así, escribirlo es más seguro: no depende de la configuración del proyecto y deja el código explícito.

Parámetros posicionales​

También se puede usar ?1, ?2..., que se refieren al primer, segundo... parámetro del método:

@Query("select a from Alumno a where a.curso = ?1 and a.edad >= ?2")
List<Alumno> buscarPorCursoYEdad(String curso, int edad);

Es más corto, pero obliga a contar, y un cambio en el orden de los parámetros altera el significado sin avisar. Es preferible la forma nombrada.

Buscar texto con like​

Los comodines % se escriben dentro de la consulta, y se unen al parámetro con concat:

@Query("select a from Alumno a where lower(a.nombre) like lower(concat('%', :texto, '%'))")
List<Alumno> buscarPorNombre(@Param("texto") String texto);

lower(...) en los dos lados hace que la búsqueda no distinga mayúsculas de minúsculas, y funciona igual en MySQL y en H2.

Filtros opcionales​

Un patrón muy habitual es un buscador con varios filtros que el usuario puede dejar vacíos. Se resuelve comprobando en la propia consulta si el parámetro es null:

@Query("""
        select a from Alumno a
        where (:curso is null or a.curso = :curso)
          and (:edadMinima is null or a.edad >= :edadMinima)
        order by a.nombre
        """)
List<Alumno> filtrar(@Param("curso") String curso, @Param("edadMinima") Integer edadMinima);

Si curso llega a null, la primera condición se cumple siempre y no filtra; si tiene valor, filtra. Con Integer (y no int) el segundo parámetro también puede ser null.

@GetMapping("/filtrar")
public String filtrar(@RequestParam(required = false) String curso,
                      @RequestParam(required = false) Integer edadMinima,
                      Model model) {

    String cursoFiltro = (curso == null || curso.isBlank()) ? null : curso;

    model.addAttribute("alumnos", repositorio.filtrar(cursoFiltro, edadMinima));
    return "alumnos";
}
nota

Un texto vacío no es null Un campo de texto de un formulario que se deja en blanco llega al controlador como "" (cadena vacía), no como null. Sin la conversión de cursoFiltro, la consulta buscaría alumnos con el curso vacío y no devolvería nada. Es el mismo detalle que vimos con @NotBlank frente a @NotNull.

6.4. Resultados que no son entidades​

Una consulta no está obligada a devolver Alumno. Según lo que se seleccione, el resultado cambia.

Un dato suelto​

@Query("select distinct a.curso from Alumno a order by a.curso")
List<String> listarCursos();

@Query("select count(a) from Alumno a where a.turno = :turno")
long contarPorTurno(@Param("turno") Turno turno);

El primero devuelve los cursos que existen, sin repetir, lo que sirve, por ejemplo, para rellenar un <select> de un formulario. El segundo devuelve un número.

Un objeto propio con varios datos​

Si se necesitan varios valores a la vez (por ejemplo, cuántos alumnos hay en cada curso), se define una clase sencilla para recogerlos. Un record de Java es lo más cómodo:

package es.centro.miproyecto.models;

public record ResumenCurso(String curso, Long total) { }

Y en la consulta se construye con select new, indicando el nombre completo de la clase (con su paquete):

@Query("""
        select new es.centro.miproyecto.models.ResumenCurso(a.curso, count(a))
        from Alumno a
        group by a.curso
        order by a.curso
        """)
List<ResumenCurso> resumenPorCurso();

count devuelve un Long, por eso el segundo componente del record es Long. Los valores de un record se leen con el nombre del componente seguido de paréntesis: resumen.curso() y resumen.total().

6.5. Consultas que modifican datos​

Una consulta update o delete escrita a mano necesita dos anotaciones más:

@Modifying
@Transactional
@Query("update Alumno a set a.curso = :nuevo where a.curso = :actual")
int cambiarCurso(@Param("actual") String actual, @Param("nuevo") String nuevo);

@Modifying
@Transactional
@Query("delete from Alumno a where a.curso = :curso")
int borrarPorCurso(@Param("curso") String curso);
  • @Modifying avisa a Spring de que la consulta no lee datos, sino que los cambia. Sin ella, Spring espera un resultado de lectura y la consulta falla.
  • @Transactional es necesario porque modificar datos exige una transacción activa (org.springframework.transaction.annotation.Transactional; lo veremos en detalle en la página de servicios).
  • El método devuelve un int con el número de filas afectadas.

Estas consultas se ejecutan como una única sentencia SQL sobre la base de datos, sin cargar antes los objetos. Es mucho más eficiente que un deleteBy derivado (que carga cada alumno y lo borra uno a uno), pero con un inconveniente: los objetos que ya estuvieran cargados en memoria no se enteran del cambio y pueden quedarse desactualizados. Si hace falta, @Modifying(clearAutomatically = true) limpia esa memoria tras la consulta.

6.6. Consultas SQL nativas​

A veces hace falta escribir SQL puro, normalmente para aprovechar una función propia de una base de datos concreta. Se indica con nativeQuery = true:

@Query(value = "select * from alumnos where curso = :curso", nativeQuery = true)
List<Alumno> buscarPorCursoNativo(@Param("curso") String curso);

@Query(value = "select * from alumnos order by rand() limit 1", nativeQuery = true)
Optional<Alumno> alumnoAlAzar();

En una consulta nativa cambian las reglas: se usan los nombres de la tabla y de las columnas (alumnos, fecha_nacimiento), no los de la clase y los atributos. Y se escribe el SQL de la base de datos concreta: rand() es de MySQL (y de H2), pero PostgreSQL usa random(), por lo que esa consulta dejaría de funcionar si se cambia de base de datos.

JPQLSQL nativo
Se escribe conClases y atributosTablas y columnas
Portabilidad entre bases de datosTotalNinguna garantizada
¿Se comprueba al arrancar?Sí: un error impide arrancar la aplicaciónNo: el error aparece al ejecutar la consulta
Funciones propias de la base de datosSolo las comunesTodas

6.7. Cuál elegir​

SituaciónOpción
Una o dos condiciones sencillasConsulta derivada del nombre
Más condiciones, filtros opcionales, agrupaciones, like combinado, o un nombre de método que se vuelve ilegible@Query con JPQL
Resultados que no son entidades (conteos, resúmenes)@Query con JPQL
Cambios masivos (update / delete)@Query con @Modifying
Una función o característica que solo ofrece tu base de datos@Query con SQL nativo

Como orden de preferencia: primero la consulta derivada, si cabe; después JPQL; y SQL nativo solo cuando no haya más remedio.

SíntomaCausa probableSolución
La aplicación no arranca y el mensaje habla de una entidad que no existe (algo como Alumnos is not mapped)En JPQL se ha escrito el nombre de la tabla en lugar del de la claseUsa el nombre de la clase: Alumno
La aplicación no arranca y el mensaje habla de un atributo desconocidoEn JPQL se ha escrito el nombre de una columna (fecha_nacimiento)Usa el nombre del atributo: fechaNacimiento
Error al arrancar pidiendo nombres para los parámetros del métodoLa consulta usa parámetros nombrados y falta @ParamAñade @Param("nombre") a cada parámetro
Un parámetro nombrado no está enlazadoEl texto de @Param no coincide con el de la consultaHaz que los dos nombres coincidan
TransactionRequiredException al ejecutar un update o deleteFalta @Transactional en la consulta que modificaAñade @Transactional junto a @Modifying
Error por no esperar un resultado de lecturaFalta @ModifyingAñádela
Unknown column en una consulta nativaSe ha escrito el nombre del atributo en lugar del de la columnaUsa el nombre de la columna (fecha_nacimiento)
