3. Entidades

Una entidad es una clase Java que JPA sabe guardar en una tabla de la base de datos. Cada objeto de esa clase se corresponde con una fila, y cada atributo con una columna. En esta página convertimos la clase Alumno de la Unidad 3 en una entidad.

3.1. De clase a entidad: @Entity​

Basta con anotar la clase con @Entity y marcar cuál de sus atributos es la clave primaria con @Id:

package es.centro.miproyecto.models;

import jakarta.persistence.Entity;
import jakarta.persistence.Id;

@Entity
public class Alumno {

    @Id
    private Long id;

    private String nombre;

    // constructor vacío, getters y setters
}

Con solo esto y un constructor vacío, Hibernate crea (si ddl-auto lo permite) una tabla llamada alumno, con una columna por cada atributo. Los nombres se derivan automáticamente: Spring Boot pasa de camelCase a snake_case y en minúsculas, de modo que un atributo fechaNacimiento genera la columna fecha_nacimiento.

nota

jakarta.persistence Todas las anotaciones de esta página pertenecen al paquete jakarta.persistence (en Spring Boot 2 y anteriores era javax.persistence).

3.2. El nombre de la tabla: @Table​

Si el nombre de la tabla debe ser distinto del de la clase, se indica con @Table:

@Entity
@Table(name = "alumnos")
public class Alumno {
    // ...
}

Es habitual usar nombres de tabla en plural; ambos criterios son válidos mientras se aplique el mismo en todo el proyecto.

3.3. La clave primaria: @Id y @GeneratedValue​

Toda entidad necesita un @Id. Lo normal es que sea un número que genera la propia base de datos, y para eso se añade @GeneratedValue:

@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
  • Se usa Long (la clase envoltorio) y no long, porque un objeto que todavía no se ha guardado no tiene identificador: su id vale null. Es la forma en que JPA distingue un objeto nuevo de uno que ya existe.
  • Tras guardar el objeto, Hibernate rellena el id con el valor que ha asignado la base de datos.

La estrategia indica cómo se genera el valor:

EstrategiaCómo funcionaCuándo usarla
IDENTITYColumna autoincremental (AUTO_INCREMENT en MySQL)La opción para MySQL
SEQUENCEUsa una secuencia de la base de datosPostgreSQL u Oracle, que tienen secuencias
UUIDGenera un identificador único universal (UUID) en Java, sin depender de la base de datosCuando no se quiere un contador numérico (ver más abajo)
AUTODeja que Hibernate elija según la base de datosMejor evitarla en MySQL (ver nota)
TABLEUsa una tabla auxiliar para generar los valoresCasos muy concretos
nota

Por qué no AUTO con MySQL MySQL no tiene secuencias. Con AUTO, Hibernate 6 las simula creando una tabla auxiliar por entidad (por ejemplo, alumno_seq), lo que sorprende a quien esperaba ver un campo autoincremental normal. Indicar IDENTITY de forma explícita evita el problema.

Identificadores UUID​

Además de un contador numérico, el identificador puede ser un UUID (Universally Unique Identifier): un valor de 128 bits que se escribe como 3f2b8a1e-7c4d-4b9a-9f10-5e6d2a8c1b07 y que, a efectos prácticos, nunca se repite. Con GenerationType.UUID, es Hibernate quien lo genera, en Java, justo antes de insertar la fila:

@Id
@GeneratedValue(strategy = GenerationType.UUID)
private UUID id;

El atributo es de tipo java.util.UUID, y ese tipo es el que habrá que indicar después en el repositorio (JpaRepository<Alumno, UUID>) y en los @PathVariable de los controladores.

IDENTITY (Long)UUID
Quién genera el valorLa base de datos, al insertarHibernate, antes de insertar
Ejemplo423f2b8a1e-7c4d-4b9a-9f10-5e6d2a8c1b07
Tamaño8 bytes16 bytes
¿Se puede adivinar el siguiente?Sí, son consecutivosNo
¿Es único entre distintas bases de datos?NoSí
Rendimiento de los índicesMejor: siempre se añade al finalAlgo peor: los valores aleatorios se reparten por todo el índice
Comodidad al escribirlo o leerloAltaBaja: es largo

Un UUID resulta útil cuando los datos se generan en varios sistemas que luego se combinan, o cuando no conviene que los identificadores revelen cuántos registros hay ni permitan recorrerlos uno a uno cambiando el número de la URL. Hay que tener en cuenta que esto no sustituye a la seguridad: que un identificador no se pueda adivinar no impide que alguien con acceso a él vea el registro, y los permisos hay que comprobarlos igualmente.

3.4. Las columnas: @Column​

Sin ninguna anotación, cada atributo se guarda en una columna con el mismo nombre y un tamaño por defecto (255 caracteres para un texto, por ejemplo). Con @Column se ajusta:

@Column(name = "fecha_nacimiento", nullable = false)
private LocalDate fechaNacimiento;

@Column(nullable = false, length = 50)
private String nombre;

@Column(nullable = false, unique = true)
private String email;
AtributoQué haceValor por defecto
nameNombre de la columnaEl del atributo, en snake_case
nullableSi admite NULL (false equivale a NOT NULL)true
lengthLongitud máxima, para columnas de texto255
uniqueSi el valor no se puede repetirfalse
precision y scaleDígitos totales y decimales de un BigDecimal19 y 2

3.5. Tipos de datos​

Hibernate traduce los tipos de Java a los de SQL. Esta tabla es orientativa, porque el tipo exacto depende de la base de datos:

Tipo JavaTipo SQL habitual
StringVARCHAR
Integer / intINT
Long / longBIGINT
Double / doubleDOUBLE
BigDecimalDECIMAL
Boolean / booleanBIT o TINYINT
LocalDateDATE
LocalDateTimeDATETIME

Para valores monetarios o cualquier cálculo que exija exactitud conviene usar BigDecimal, no double.

Enumerados: @Enumerated​

Un enum de Java se guarda con @Enumerated:

public enum Turno {
    MANANA, TARDE
}
@Enumerated(EnumType.STRING)
@Column(nullable = false, length = 10)
private Turno turno;

Hay dos formas de guardarlo:

EnumType.STRINGEnumType.ORDINAL
Qué se guardaEl nombre ("TARDE")La posición (1)
Legibilidad en la base de datosAltaHay que saber qué número es cada valor
Si se reordena o inserta un valor en el enumSin consecuenciasLos datos existentes pasan a significar otra cosa

ORDINAL es el valor por defecto, pero es una trampa: añadir un valor en mitad del enum desplaza los números de los siguientes y corrompe los datos ya guardados. Usa siempre EnumType.STRING.

3.6. Atributos que no se guardan: @Transient​

A veces una clase tiene atributos que solo existen en memoria y no deben ocupar una columna: un valor calculado, o una marca que solo se usa en la pantalla. Se marcan con @Transient:

@Transient
private boolean seleccionado;

JPA los ignora al guardar y al leer. Si se escribe un atributo así sin @Transient, Hibernate intentará crear una columna para él.

3.7. Requisitos de la clase​

Para que una clase funcione como entidad debe cumplir unas condiciones:

  • Tener un constructor sin argumentos (puede ser protected). Hibernate lo usa para crear los objetos al leer las filas. Si se escriben otros constructores, hay que añadir también el vacío.
  • No ser final, ni tener métodos final: Hibernate crea clases derivadas (proxies) para algunas operaciones, como veremos con las relaciones.
  • Tener un atributo anotado con @Id.

Al anotar los atributos (no los métodos getter), Hibernate lee y escribe directamente los campos. Los getters y setters siguen haciendo falta, pero para el resto de la aplicación: los usan Thymeleaf y el binding de los formularios.

3.8. La entidad Alumno completa​

Juntando todo, y conservando las anotaciones de validación de la Unidad 3:

package es.centro.miproyecto.models;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Past;
import jakarta.validation.constraints.Size;
import java.time.LocalDate;
import org.springframework.format.annotation.DateTimeFormat;

@Entity
@Table(name = "alumnos")
public class Alumno {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @NotBlank(message = "El nombre es obligatorio")
    @Size(min = 2, max = 50, message = "El nombre debe tener entre 2 y 50 caracteres")
    @Column(nullable = false, length = 50)
    private String nombre;

    @NotBlank(message = "Debes elegir un curso")
    @Column(nullable = false, length = 10)
    private String curso;

    @NotNull(message = "La edad es obligatoria")
    @Min(value = 16, message = "La edad mínima es 16 años")
    @Max(value = 99, message = "La edad máxima es 99 años")
    @Column(nullable = false)
    private Integer edad;

    @NotBlank(message = "El email es obligatorio")
    @Email(message = "El email no tiene un formato válido")
    @Column(nullable = false, unique = true)
    private String email;

    @NotNull(message = "La fecha de nacimiento es obligatoria")
    @Past(message = "La fecha de nacimiento debe ser anterior a hoy")
    @DateTimeFormat(iso = DateTimeFormat.ISO.DATE)
    @Column(name = "fecha_nacimiento", nullable = false)
    private LocalDate fechaNacimiento;

    @NotNull(message = "Debes elegir un turno")
    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 10)
    private Turno turno;

    public Alumno() { }

    // getters y setters de todos los atributos
}

Validación y @Column: dos cosas distintas​

El mismo requisito aparece dos veces: @NotBlank y @Column(nullable = false). No es redundancia inútil, cada una cumple una función distinta:

Validación (@NotBlank, @Size...)JPA (@Column(nullable = false, length = 50))
Quién la aplicaSpring, en Java, al validar el formularioLa base de datos, al guardar
Para qué sirveAvisar al usuario con un mensaje claroGarantizar la integridad aunque el dato llegue por otra vía
Si se incumpleError en el formulario, con th:errorsExcepción al guardar

Conviene mantener ambas: la primera da una buena experiencia al usuario, y la segunda es la red de seguridad.

nota

Ahora la entidad tiene id La clase Alumno de la Unidad 3 no tenía identificador. Con él aparece el riesgo que mencionamos en la página de binding: si alguien envía un POST con id=1, el save interpretará que se trata del alumno 1 y lo actualizará en lugar de crear uno nuevo. En el ejemplo integrador veremos cómo evitarlo.

3.9. Dónde se colocan las entidades​

Spring Boot busca las entidades en el paquete de la clase principal (la anotada con @SpringBootApplication) y en todos sus subpaquetes. Por eso las colocamos en models, que cuelga de ese paquete:

es.centro.miproyecto/
├── MiProyectoApplication.java
├── controllers/
├── services/
├── repositories/
└── models/
    ├── Alumno.java
    └── Turno.java

3.10. Ver la tabla creada​

Con la configuración de la página anterior (ddl-auto=update y show-sql=true), al arrancar la aplicación aparece en la consola la sentencia que crea la tabla, parecida a esta (simplificada):

create table alumnos (
    id bigint not null auto_increment,
    nombre varchar(50) not null,
    curso varchar(10) not null,
    edad integer not null,
    email varchar(255) not null,
    fecha_nacimiento date not null,
    turno varchar(10) not null,
    primary key (id)
)

Y se puede comprobar desde el cliente de MySQL del contenedor:

docker compose exec mysql mysql -ucentro_user -pcentro_pass centro
DESCRIBE alumnos;

El orden de las columnas, y la forma exacta de la columna turno (puede aparecer como enum según la versión de Hibernate), pueden variar. Si se usa el perfil h2, la tabla se ve en la consola web.

SíntomaCausa probableSolución

Table 'centro.alumnos' doesn't existddl-auto está en none o validateUsa update mientras desarrollas
Data truncated for column / Data too longEl valor supera el length de la columnaAumenta el length o valida el tamaño con @Size
Duplicate entry '...' for keySe repite un valor de una columna uniqueControla el valor antes de guardar
Unknown column tras cambiar la entidadLa tabla ya existía con otro esquema y update no la modificaEn desarrollo, borra la tabla o el volumen y deja que se cree de nuevo
