4. Métodos de petición HTTP

El método (o verbo) expresa la intención de la petición sobre el recurso indicado en la ruta. Elegirlo bien no es una formalidad: de él dependen el comportamiento de las cachés, de los proxies, de los navegadores y de los mecanismos de reintento.

4.2. Las tres propiedades que hay que entender​

Seguro (safe)​

📌 Un método es seguro si no modifica el estado del servidor. Es de sólo lectura.

Consecuencia práctica: un buscador, un antivirus corporativo o el pre-cargador del navegador pueden lanzar GET a cualquier enlace sin avisar. Por eso esto es un desastre:

<!-- ❌ NUNCA -->
<a href="/alumnos/42/borrar">Eliminar alumno</a>

Bastaría con que un rastreador siguiera el enlace para borrar el registro.

Idempotente​

📌 Un método es idempotente si ejecutarlo N veces produce el mismo estado final que ejecutarlo una sola vez.

  • DELETE /alumnos/42 — el alumno queda borrado; repetirlo no cambia nada más. Idempotente.
  • POST /alumnos — cada llamada crea un alumno nuevo. No idempotente.

Esto importa cuando la red falla: si un cliente no recibe respuesta, sólo puede reintentar sin riesgo una operación idempotente.

Cacheable​

📌 Una respuesta es cacheable si puede almacenarse y reutilizarse en peticiones posteriores. GET lo es por defecto; los métodos de escritura, no.

:::note Todo depende de tu implementación Que GET sea "seguro" es una convención del protocolo, no una garantía técnica. Si programas un @GetMapping que borra registros, nada te lo impide — y habrás roto el contrato de HTTP con consecuencias muy difíciles de depurar. :::

4.3. Los métodos uno a uno​

GET​

Solicita la representación de un recurso. Los parámetros van en la query string, nunca en el cuerpo.

GET /api/alumnos?curso=2DAW&orden=nombre HTTP/1.1
Host: api.centro.es
Accept: application/json

⚠️ La query string queda registrada en los logs del servidor, en el historial del navegador y en proxies intermedios: nunca envíes contraseñas o tokens por ahí.

POST​

Envía datos para que el servidor los procese. Es el método "comodín": creación de recursos, formularios, inicios de sesión, operaciones que no encajan en el resto.

POST /api/alumnos HTTP/1.1
Content-Type: application/json

{"nombre":"Lucía Márquez","curso":"2DAW"}

Respuesta correcta a una creación:

HTTP/1.1 201 Created
Location: /api/alumnos/42

PUT​

Sustituye por completo el recurso. Los campos que no envíes se consideran ausentes.

PUT /api/alumnos/42 HTTP/1.1
Content-Type: application/json

{"nombre":"Lucía Márquez","email":"lucia@centro.es","curso":"2DAW"}

PATCH​

Aplica una modificación parcial:

PATCH /api/alumnos/42 HTTP/1.1
Content-Type: application/merge-patch+json

{"curso":"2DAM"}

AlcanceRecurso completoCampos indicados

DELETE​

DELETE /api/alumnos/42 HTTP/1.1

Respuestas habituales: 204 No Content (borrado sin cuerpo) o 200 OK (devolviendo el recurso eliminado).

HEAD y OPTIONS​

  • HEAD: idéntico a GET pero el servidor devuelve sólo cabeceras. Útil para comprobar si un recurso existe o su tamaño sin descargarlo.
  • OPTIONS: informa de qué métodos admite un recurso. Es la base de las peticiones de comprobación previa (preflight) de CORS.
OPTIONS /api/alumnos HTTP/1.1
---
HTTP/1.1 204 No Content
Allow: GET, POST, OPTIONS

4.4. Mapeo en Spring Boot​

  • API REST completa
  • De dónde salen los datos
  • Formularios HTML
@RestController
@RequestMapping("/api/alumnos")
public class AlumnoController {

    private final AlumnoService servicio;

    public AlumnoController(AlumnoService servicio) {
        this.servicio = servicio;
    }

    @GetMapping
    public List<AlumnoDTO> listar(@RequestParam(required = false) String curso) {
        return servicio.buscar(curso);
    }

    @GetMapping("/{id}")
    public AlumnoDTO obtener(@PathVariable Long id) {
        return servicio.obtener(id);   // lanza 404 si no existe
    }

    @PostMapping
    public ResponseEntity<AlumnoDTO> crear(@Valid @RequestBody AltaAlumnoRequest req) {
        AlumnoDTO creado = servicio.crear(req);
        return ResponseEntity
                .created(URI.create("/api/alumnos/" + creado.id()))  // 201 + Location
                .body(creado);
    }

    @PutMapping("/{id}")
    public AlumnoDTO reemplazar(@PathVariable Long id,
                                @Valid @RequestBody AlumnoRequest req) {
        return servicio.reemplazar(id, req);
    }

    @PatchMapping("/{id}")
    public AlumnoDTO modificar(@PathVariable Long id,
                               @RequestBody Map<String, Object> cambios) {
        return servicio.modificarParcial(id, cambios);
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)     // 204
    public void eliminar(@PathVariable Long id) {
        servicio.eliminar(id);
    }
}

Un formulario HTML sólo admite GET y POST:

<form action="/alumnos" method="post">
  <input name="nombre" required />
  <button type="submit">Guardar</button>
</form>

Para simular PUT o DELETE desde un formulario se usa el filtro HiddenHttpMethodFilter de Spring junto a un campo oculto _method, o bien se envía la petición desde JavaScript con fetch.

4.5. Diseño de rutas: buenas prácticas​

❌ Evita✅ Prefiere
/getAlumnosGET /alumnos
/alumnos/crearAlumnoPOST /alumnos
/borrarAlumno?id=42DELETE /alumnos/42
/alumno (singular)/alumnos (plural, colección)
/api/v1/Alumnos/api/v1/alumnos (minúsculas)

📌 Regla mnemotécnica. El sustantivo va en la URL; el verbo, en el método HTTP.
